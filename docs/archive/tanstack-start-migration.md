## 2. 官方资料确认的适配方式

建议采用 `TanStack Start`（全栈框架）加现有 `Vite`（构建工具），优先使用单页应用模式，保留组件和样式。单页模式是本项目的选择，官方支持多种渲染方式，没有要求所有工具采用它。

官方从零指南直接演示了：按钮调用服务端函数，服务端使用 `node:fs`（本地文件系统接口）读取和写入计数文件，保存后刷新页面数据。这是与我们的文件编辑需求最接近的官方入门例子。[从零构建指南](https://tanstack.com/start/latest/docs/framework/react/build-from-scratch)，章节“配置”“应用根入口”“第一个路由”。

`Server Functions`（服务端函数）负责应用内部的读取和修改；浏览器调用它们时，框架处理请求与序列化。`Server Routes`（服务端接口路由）适合需要明确网络接口的外部调用，例如独立命令行客户端。两者可复用同一份服务逻辑。[官方服务端函数说明](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)，章节“用途”“文件组织”；[官方接口路由说明](https://tanstack.com/start/latest/docs/framework/react/guide/server-routes)。

普通 `loader`（路由数据加载逻辑）并不保证只在服务端执行。项目文件读取、写入和检查应放在服务端函数或专用服务模块中，页面与路由通过它们请求数据。[官方运行位置说明](https://tanstack.com/start/latest/docs/framework/react/guide/code-execution-patterns)，章节“错误的加载逻辑假设”。

单页模式仍保留服务端函数；要读写文件，仍需运行本地服务，而不是只打开静态页面。另外，它会在构建时预渲染根外壳，所以用户项目的数据不要在根外壳构建过程中读取。[官方单页模式说明](https://tanstack.com/start/latest/docs/framework/react/guide/spa-mode)，章节“没有服务端渲染时的服务能力”“外壳中的动态数据”。

`TanStack Query`（异步数据管理库）可以继续管理文件读取结果、保存状态和保存后的刷新。官方明确：路由协调导航，查询库管理数据；采用整合方案时不要再创建另一份缓存或重复添加提供器。[官方查询库整合说明](https://tanstack.com/start/latest/docs/framework/react/guide/tanstack-query)，章节“按路由创建查询客户端”“修改后刷新”。

## 4. 我们的迁移方案

当前网页是 `React Router 7`（现有路由库）的声明式模式，页面仍主要是骨架。建议按三个阶段推进，由用户主要手写代码；每阶段先讲用途与完成标准。

### 第一阶段：接通框架和现有页面

- 加入框架与它的路由库，保留现有构建工具、界面库、查询库和组件体系。
- 配置框架插件、单页模式、类型检查及样式入口。框架插件应位于界面库构建插件之前，这是官方配置要求。
- 建立 `src/router.tsx`（路由入口）和 `src/routes/__root.tsx`（根路由），由框架接管现有网页入口职责。`src/routeTree.gen.ts`（生成的路由树）由工具生成，不手改。
- 新路由文件导入已有页面和布局；转换导航、动态参数和子页面位置的路由接口。按框架入门配置启动，不把独立路由教程里的提供器和插件重复叠加到框架上。
- 阶段验收：现有页面可直接打开、刷新和前后导航，样式正常，类型检查与构建通过。

当前组织与项目地址可以先机械转换，以验证框架接入；这不代表组织管理仍是最终产品必需功能。最终地址和导航要按已经讨论的本地工具方向另行确认，不能因为参考平台有组织结构就保留其全部产品分工。

来源：[官方现有路由迁移说明](https://tanstack.com/router/latest/docs/how-to/migrate-from-react-router)，路由和导航部分；框架入口和启动方式优先参考前面的从零构建指南。迁移说明还涉及我们未采用的数据路由和其他框架功能，不将其全部步骤套用到本项目。

### 第二阶段：接通本地文件操作

- 由本地启动程序明确目标项目目录；网页读取当前项目信息与体系文件。
- 把已有检测、主题生成和文件写入整理为独立服务逻辑，再由服务端函数调用。保留能复用的校验和测试；旧的领取修改接口不会自动变成新保存流程。
- 查询结果与编辑草稿分开。保存请求经过校验、外部修改检查和恢复准备后更新文件，再刷新页面中的已保存数据。
- 阶段验收：重启后可读回保存结果，目标范围以外的文件不会被修改，外部修改与保存失败有可理解的结果。

这部分服务端函数接口与框架规则有官方依据；目标目录、保存格式、生成文件和恢复方式属于本项目设计，尚未完成实现约定。

### 第三阶段：成为可运行的本地工具

- 开发阶段与工具分发分开验证。开发时由构建工具运行框架，分发时提供构建好的网页和本地服务，用户不需要自己启动我们的编辑器开发服务器。
- 当前官方构建工具对应的本地运行指南使用 `Nitro`（服务构建与运行适配层），参考项目也使用它。建议沿这条路径核对本地运行产物，而不是假定框架自带所有服务启动工作。
- 阶段验收：构建后的程序在本地启动后，页面与服务端函数均可用；能针对选定项目保存与检查，关闭后停止服务。分发与离线能力仍需实际验证。

来源：[官方运行指南](https://tanstack.com/start/latest/docs/framework/react/guide/hosting)，章节“服务适配层”“本地运行环境”。它支持其他运行方式，本项目优先核对本地文件操作需要的运行环境。

## 5. 工程实践与版本核对

- 文件系统依赖只放在服务端实现中；客户端产物不得包含文件操作模块。
- 路由负责地址和页面组织，查询库负责读取结果与修改状态，组件状态保存未提交草稿。保存后刷新实际拥有这份数据的缓存，不重复刷新所有层。
- 根外壳不要依赖用户的项目目录。单页外壳构建期间没有某个未来用户的文件可读。
- 本地服务仍需限制项目范围和请求来源。页面上的限制不能代替服务端校验；不会因为只在本机运行就自动正确。
- 参考项目的兼容层、云端部署规则、认证、错误上报与历史版本问题按适用条件阅读，不整套加入我们的工具。

本轮注册表核对：框架当前版本为 1.168.61，路由为 1.170.42；框架声明 `Node.js`（本地运行环境）最低 22.12.0，`Vite`（构建工具）最低第七版。项目当前使用第八版构建工具和第十九版界面库，满足这两项声明；本轮未运行本地运行环境版本检查，正式安装前还需核对。

参考提交的工作区配置指定框架 ^1.168.60、路由 ^1.170.41，和本轮当前发布版本接近，但两者不是同一组锁定版本。本轮不据此自动升级任何依赖。

当前 `apps/web/tsconfig.app.json`（网页类型配置）启用了 `verbatimModuleSyntax`（保留模块声明的编译选项）；官方从零指南建议关闭该选项以避免服务端内容进入客户端。正式迁移时按最终安装版本核对这一项，并验证客户端产物。

官方概述仍称框架处于候选发布阶段，而注册表包已经使用第一版编号。这里如实记录两种信息，不仅凭版本号宣称整个框架路径已完全成熟。[官方概述](https://tanstack.com/start/latest/docs/framework/react/overview)；版本元数据来源为软件包官方发布记录。
