# 运行时连接设计体系服务：第一轮研究

- 核对日期：2026-10-12。
- 问题：把主题变量和语义映射保存到服务，用户应用运行时请求这些数据，再渲染页面，是否可行、有没有先例、会改变什么？
- 状态：研究材料，尚未成为项目决定。
- 2026-10-12 后续澄清：用户目标是开发阶段的本地编辑工具，不是生产应用远程换肤。本文保留研究历史，当前方向见 docs/phases/03-web/product-flow.md（产品流程），不据此实现运行时主题服务。
- 核对方式：阅读固定提交源码、项目现状和官方资料正文；没有安装工具、运行原型或修改业务代码。功能存在不等于市场需求已被验证，本轮没有调查用户规模。

## 先说结论

这个想法在技术上可行，而且有直接的产品先例。更准确地说，它是“远程主题配置”：服务管理设计定义，应用按约定获取并使用它们。

运行时主题主要解决“已经接入的界面，怎样更新设计值”。现有源码的接入、变量名称变化和使用检查仍需要另外处理。服务保存成功、发布成功、某个页面应用成功，是三个不同状态。

已读仓库路径：`apps/studio/data/projects/project-detail-query.ts`（项目详情查询）、`apps/studio/data/database/schemas-query.ts`（数据库结构查询）和 `apps/studio/data/sql/execute-sql-mutation.ts`（数据库查询执行）。网页获取项目连接信息，通过平台接口执行数据库查询；不是把数据库凭据直接交给任意页面组件连接数据库。

这些文件没有提供面向用户项目的远程主题发布协议。数据库访问可以帮助理解服务分工，但不能证明主题服务应该照搬数据库接口。此前已说明这一缺口，以下使用对应领域的官方资料补充。

## 2. 有没有人实际这样做

| 已核实的先例 | 官方资料确认的做法 | 能证明到哪里 |
| --- | --- | --- |
| `commercetools InStore POS`（门店收银系统） | 启动时请求服务保存的租户主题，与应用内默认主题合并，交给 `MUI`（界面组件库）。修改下次加载生效，不实时推送。 | 这是直接的运行时远程主题先例，但适用于它自己的组件和应用。 |
| `Firebase Remote Config`（远程配置服务） | 应用获取云端参数，缓存后选择何时启用，能够改变外观和行为；支持内置默认值与配置版本管理。 | 证明远程外观配置的通用机制存在，但它不负责整理设计语义或迁移项目源码。 |

收银系统的主题包含颜色、字体、间距、圆角和组件覆盖。它只保存当前主题，没有服务端历史版本，需要自行备份。因此，“有主题接口”本身不代表已经具备完整版本治理。

来源：[主题接口参考](https://docs.commercetools.com/instore/customization/pos-theme-api)，章节“请求怎样在应用中生效”“读取主题”；[网页接入远程配置](https://firebase.google.com/docs/remote-config/web/get-started)，第 3、6、7 步；[配置模板与版本](https://firebase.google.com/docs/remote-config/templates)，章节“模板生命周期与版本”。这里只核实先例，不建议引入这两个产品。

## 3. 数据怎样变成页面样式

可以把整个过程理解为：

**网页编辑设计定义 → 服务发布一份主题 → 用户应用读取主题 → 转换为浏览器能使用的样式 → 已接入的组件显示结果。**

服务不需要让每个按钮单独查询数据库。应用可以一次获取当前主题，统一应用到页面或某个主题区域。这是基于资料的项目推断，不是某个库的强制要求。

浏览器已有两种基础方式：

| 方式 | 应用怎样使用 | 需要承担的工作 |
| --- | --- | --- |
| 返回 `JSON`（结构化数据） | 项目读取变量与映射，设置 `CSS custom properties`（样式自定义变量）。 | 项目需要数据校验、转换和加载逻辑。 |
| 返回 `CSS`（层叠样式表） | 服务生成可用样式，页面用 `link`（外部资源标签）加载。 | 服务需要生成样式，项目仍需处理加载失败、层叠优先级和版本。 |

第二种也是运行时连接，不必先下载到源码仓库；但服务应交付浏览器可用的样式，不能把未经构建处理的主题指令直接当成浏览器样式。

官方机制依据：[样式变量规范](https://www.w3.org/TR/css-variables-1/#defining-variables)，第 2 节说明继承、层叠和脚本读写；[网页标准](https://html.spec.whatwg.org/multipage/links.html#link-type-stylesheet)，第 4.6.8.23 节说明外部样式表获取与应用。两种交付方式均属可选方案。

## 4. 对当前样式工具的边界

本项目 `Tailwind CSS`（原子样式工具）的依赖声明、锁定文件和实际安装均为第四版 4.3.3；本轮读取的官方文档标注第四版 4.3。

官方“何时使用行内样式”章节直接展示了：颜色可以来自数据库或接口，也可以先设置变量，再由固定工具类引用。[官方动态值示例](https://tailwindcss.com/docs/styling-with-utility-classes#when-to-use-inline-styles)。这说明运行时设计值与当前工具并不冲突。

但它在构建时扫描源码并生成样式。接口运行时返回一个新的类名，不会自动补出对应规则。[官方类名扫描说明](https://tailwindcss.com/docs/detecting-classes-in-source-files)，章节“动态类名”；[官方主题变量说明](https://tailwindcss.com/docs/theme)，章节“变量与工具类的关系”“引用其他变量”。

| 修改内容 | 对我们这个方向的判断 |
| --- | --- |
| 已存在变量的颜色、圆角、尺寸值 | 如果生成的样式仍引用这些变量，可以运行时更新。 |
| 已存在语义名称改为引用另一项设计值 | 引用完整、类型适合且没有循环时，可以随主题更新。 |
| 增加、删除或改名一个组件正在使用的语义 | 需要检查源码与当前构建结果的兼容性；删除名称可能让旧页面失效。 |
| 新增工具类、响应式断点或组件结构 | 不能只靠返回变量保证生效；可能需要重新构建、修改源码，或另有明确的运行时样式实现。 |

这些限制针对当前构建方式，不代表所有主题引擎只能改值。上面的收银系统允许组件覆盖，是因为它已经实现了相应的主题解释和应用能力。

`shadcn/ui`（项目当前采用的组件体系）官方建议使用语义样式变量。当前控制台样式也具有这种映射，但它是控制台自己的固定主题，不能据此认为任意用户项目都已接入。[官方主题说明](https://ui.shadcn.com/docs/theming)，章节“主题”“新增设计变量”。

## 5. 运行时连接需要讨论哪些约定

以下是研究后的项目建议，均未确定实现：

- **首屏与失败处理**：先显示内置或缓存主题，还是等待主题请求？前者可能随后变色，后者增加等待。首次访问没有缓存，需要默认值或明确的失败状态。官方远程配置指南提供了启动启用、加载画面后启用、下次启动启用等可选策略，并建议保留内置默认值。[官方加载策略](https://firebase.google.com/docs/remote-config/loading)。
- **发布与生效时点**：草稿不能直接影响生产页面。要讨论应用固定某个版本，还是在受控时点获取新版本；已经打开的页面未必同时更新。固定版本意味着新发布不自动生效，跟随更新则需要缓存与回退约定。
- **数据兼容与完整性**：设计值的修改，与变量改名、删项要区分。语义引用应检查目标、类型和循环；一次应用完整主题，避免部分字段混用两个版本。浏览器的变量默认值不能修复所有类型错误。[样式变量规范第 2.3、3.1 节](https://www.w3.org/TR/css-variables-1/#invalid-variables)。
- **读取与编辑分开**：普通页面只需要可发布主题的读取能力，不应拥有编辑凭据。发送给浏览器的数据可以被用户读取。官方远程配置接入说明也明确提示不要在客户端参数中保存秘密。[官方默认参数说明](https://firebase.google.com/docs/remote-config/web/get-started#in-app-default-parameter-values)。

若未来用户项目采用 `SSR`（服务端渲染），还需让首屏和客户端使用兼容的主题快照。`React`（界面库）要求客户端初次生成内容与服务端一致；只有主题差异实际改变了属性或结构时，才能据此判断存在接管不一致，不能把任何颜色变化都称作接管错误。当前项目不因这一点改框架。[官方接管约束](https://react.dev/reference/react-dom/client/hydrateRoot#caveats)。

## 6. 设计定义与本地检查如何共存

运行时主题决定“页面现在用什么值”；本地扫描和 `lint`（静态检查）判断“源码用了哪些定义，是否写死值、引用了不存在的名称或违反约定”。只请求主题无法自动获得源码使用情况。

如果服务同时保存检查规则，检查工具仍需要读取与目标主题版本匹配的规则和名称清单，以及可执行的本地规则实现。页面不需要运行这些检查；让检查直接跟随服务最新草稿，也会使同一份代码的检查结果不稳定。这是基于当前产品边界的推断，没有在本轮选定检查库或规则包。

设计数据也不必只是一段样式文件。`DTCG`（设计变量社区组）的 2025.10 格式规范定义名称、类型、值和别名引用，能作为数据模型参考；它是社区组发布的规范，不是万维网联盟正式标准，也不规定我们的数据库、网络接口或发布方式。[格式规范](https://www.designtokens.org/tr/2025.10/format/)，第 5、7、8 节和文档状态说明。

## 7. 它会怎样改变现有产品流程

现有产品流程是“编辑 → 确认迁移 → 生成待应用版本 → 本地执行应用命令”。如果采用运行时主题，可能改为：

**第一次接入：扫描项目 → 整理与迁移引用 → 接入主题读取和默认主题。**

**之后改设计值：网页编辑 → 预览与检查 → 发布主题版本 → 应用按约定获取并启用。**

变量改名、删除、增加新样式能力等仍可能需要本地修改与重新发布代码。已有命令行能力仍可负责这些工作；不需要把所有修改都改成远程运行。

收益可能是多项目、多品牌或多租户统一更新外观，减少仅改值时的源码修改。代价是主题服务开始参与生产页面运行，需要维护可用性、版本兼容和加载体验。两者都是项目推断；本轮资料没有证明我们的目标用户会为此采用产品。

## 仍待验证

最关键的产品问题是：用户是否需要“已经发布的应用，更新设计值时不用重新发布代码”？如果需要，这个方向有明确用途；如果不需要，集中管理设计体系也可以继续以文件或包交付，集中保存与运行时连接是两个独立选择。

后续验证应覆盖弱网、首次访问、服务不可用、旧代码读取新主题、明暗切换和版本回退，并确认源码检查使用哪个版本。本轮没有进行这些实验，所以不宣称性能、兼容性或接入成本已经验证。

本轮只新增这份研究记录，原有产品流程与技术决策保持原状态。侧栏和框架迁移不在本轮范围内。
